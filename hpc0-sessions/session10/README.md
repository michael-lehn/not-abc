# Session 10 — Assembly & Code Generation

## Preparation

Before this session, students should watch:

- [ULM Generator: First Steps](https://www.youtube.com/watch?v=ALWl-W_5raE)
- [ULM Assembler: First Steps](https://www.youtube.com/watch?v=Cdep8UA3E5g)

The worksheet assumes that the tools generated by `ulm-generator` are already
familiar at a basic level and were installed in Session 00.

## Lecturer Notes

This session deliberately starts bottom-up. Students first work directly with
assembly instructions and the tools generated from an ISA description before we
introduce a small code-generator interface.

The progression is:

1. assemble, inspect, debug, and run a tiny program;
2. introduce jumps and labels;
3. implement a small decimal-input program and compare it with equivalent ABC programs;
4. introduce leaf functions and return addresses;
5. let non-leaf functions fail before introducing the stack;
6. use the stack to save return addresses and test the mechanism with recursion;
7. recognize recurring assembly-generation patterns and begin implementing a code generator;
8. extend the code generator independently with another binary instruction.

A central teaching principle is to expose the problem before introducing the
abstraction that solves it. In particular, the stack is motivated by the
failure of the naive non-leaf-function example, and the code generator is
motivated only after students have written enough assembly by hand to see which
details become repetitive.

### ISA Used in the Worksheet

The preparation videos use `ulm-ice40.isa`, the instruction set implemented by
ULM-on-iCE. The worksheet uses the slightly extended `hpc0.isa`.

The additional instructions are mainly conveniences for the course. In
particular, `hpc0.isa` provides direct 64-bit multiplication and division. This
keeps the focus of this session on assembly programming and code generation
rather than on implementing these operations from simpler instructions.

### Function Calls and the Stack

The leaf-function example should be explored in the debugger. Students should
explicitly observe that `call` stores the return address in a register and that
`ret` transfers control back to this address.

For non-leaf functions, resist explaining the solution too early. Let students
observe how a nested call overwrites the return address. The stack example then
solves a problem they have already encountered.

In the stack-based examples, `%1` is used as the stack pointer and `%2` as the
return-address register. Later parts of the compiler project will assign
additional special roles to registers.

The recursion exercise is useful as a final sanity check: if the mechanism
works recursively, students have good evidence that they understood why saving
return addresses on a stack solves the general problem.

### First Steps with the Code Generator

The second half of the session makes the transition from hand-written assembly
to generated assembly. The important idea is not the amount of code in
`gen.abc`, but the interface: a caller can request operations such as loading a
constant into a free register without choosing the physical register or
spelling out the assembly instruction.

The implementation is intentionally developed by following the `TODO`
assertions. Students compile and run the test program, replace the stub where
execution stops, and repeat. This keeps the implementation manageable and makes
the execution path visible.

The simple register allocator is deliberately primitive. Registers `%0` through
`%3` are kept out of the general-purpose pool; allocation starts at `%4`. The
purpose here is to establish the abstraction represented by `GenReg`, not to
discuss sophisticated register allocation.

When `genConstant()` is introduced, make sure students understand the `printf`
format string, in particular that `%%` emits a literal `%`. This detail will
recur throughout the code generator.

After the first tiny generator is complete, students redirect its output to an
assembly file, assemble that generated file, and execute it in the debugger.
This is an important moment: the ABC program is now producing assembly that is
subsequently translated into machine code and executed on the virtual ULM
machine.

### Extending the Generator

The final task deliberately provides only a test program and the expected
assembly output. Students have already seen the necessary pattern and should
determine themselves that both the `GenInstr` interface and the implementation
of `genInstr()` need to be extended for `GEN_ADD`.

This is also the bridge to the later compiler sessions. The code generator
developed here is not a throwaway exercise: it will become part of the compiler
project. Later, the parser and expression-tree code can generate code through
this interface rather than emitting assembly directly.

At the end of the course, students will also receive another implementation of
the same general interface that generates LLVM IR. This provides a concrete
example of how a code-generator interface can hide target-specific details.
